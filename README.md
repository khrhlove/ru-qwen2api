## Основные возможности

| Возможность | Описание |
|---|---|
| 🔄 **Мультиаккаунтный пул** | Пул учётных данных; выбор аккаунта = «самый свободный + дольше всех не использовавшийся», ограничение числа запросов в обработке на один аккаунт, чтобы один аккаунт не долбили подряд |
| 🔑 **Оба вида учётных данных** | ① вставить Bearer-токен (скопировать через F12); ② просто указать email + пароль — шлюз сам проходит `signin → refresh`, получает access_token и **автоматически перелогинивается** при 401 |
| 🛡️ **Ступенчатое охлаждение** | 401 ⇒ длинное охлаждение (по умолчанию 1800 с); исчерпание квоты / 429 / риск-контроль ⇒ мягкое охлаждение с экспоненциальным откатом (максимум 1 ч); состояние сохраняется на диск и не теряется при перезапуске |
| 🧠 **Режимы мышления** | Параметр запроса `thinking: auto / thinking / fast` — дословно соответствует трём режимам веб-версии «Авто / Принудительный / Быстрый»; поддерживается `reasoning_effort` (low/medium/high) |
| 💭 **Настоящее мышление** | Пошаговая сводка «глубокого мышления» от апстрима после diff передаётся через `reasoning_content` — она не выдумана; `usage.output_tokens_details.reasoning_tokens` тоже передаётся |
| 🤖 **Режим Agent** | `qwen3.8-max-agent` / `qwen3.8-flash-agent` работают через `chat_type=agent_mode`: **сервер сам планирует и выполняет инструменты** (bash / write_file / ask_user), весь цикл `think → tool_call → think → answer` проходит за один запрос. По замерам, фраза «напиши hello.py и запусти» = 4 раунда инструментов, **самостоятельное исправление ошибок** (после неудачи `cd /home/user` сам выполнил `pwd`+`find` и нашёл реальный путь в песочнице), результат за 11 секунд. Траектория инструментов записывается в журнал запросов (поле `tools`). ⚠️ Когда нужно уточнение, апстрим вызывает интерактивный инструмент `ask_user`, на который однораундовый API ответить не может; файлы-артефакты вместе с ответом не отдаются (апстрим выдаёт только список имён файлов) |
| ⚡ **Потоковый + непотоковый режим** | Исходящий запрос всегда с `stream:true`, непотоковый режим агрегируется локально (у апстрима только одна ветка, поведение предсказуемо); поддерживается `stream_options.include_usage` |
| 🤝 **Три протокола на входе** | `POST /v1/chat/completions` (OpenAI) · `POST /v1/messages` (Anthropic Messages, подключается Claude Code) · `POST /v1/responses` (форма Responses) |
| 🛠️ **Вызов инструментов (эмуляция)** | Все три входа понимают `tools` / `tool_choice`. У апстрима нет канала вызова функций: шлюз рендерит схему в системный протокол, а JSON из ответа модели разбирает обратно в `tool_calls` (на стороне Anthropic — блоки `tool_use`, на стороне Responses — элементы `function_call`). **Многораундовая передача тоже работает**: `assistant.tool_calls` + `role=tool` / `tool_use`+`tool_result` / `function_call`+`function_call_output` — всё рендерится в prompt. ⚠️ Это адаптация протокола, а не нативная возможность: если модель не соблюдает договорённость, происходит откат к обычному тексту, **вызов никогда не подделывается** |
| 🖼️ **Ввод изображений (мультимодальность)** | Сегменты content в chat поддерживают изображения: URL / data URI / «голый» base64, принимаются все три формы записи — `image_url` / `input_image` / Anthropic `image`; путь `getstsToken` → загрузка в OSS → `files[]` (`file_class=vision`), загрузка и отправка идут **с одного аккаунта** |
| 🎨 **Генерация/редактирование изображений** | `POST /v1/images/generations` (текст→изображение + **изображение→изображение**) и `POST /v1/images/edits` (multipart-вход). Набор полей соответствует спецификации image-adapter; `image` поддерживает URL / data URI / «голый» base64, **референсные изображения автоматически загружаются через `getstsToken` → PUT с подписью OSS V4** |
| 🎬 **Генерация видео** | **Нативный протокол Volcano Ark**: `POST/GET/DELETE /api/v3/contents/generations/tasks`. Создание возвращает только `id`, шесть состояний, `content.video_url`, идемпотентность, колбэки, сохранение задач на диск. Поддерживаются 720P/1080P × 5/10/15 с × 6 вариантов соотношения сторон, текст→видео / первый кадр / первый+последний кадр / несколько референсных изображений |
| 🖼️ **Медиа-артефакты** | Изображения возвращаются как подписанные прямые ссылки CDN (`cdn.qwenlm.ai`), опционально с inline-`b64_json`; видео возвращает URL артефакта задачи `tsk_` |
| 📄 **Разбор файлов** | Загрузка через `POST /v1/files` (PDF/txt/любой документ) → ссылка на `file_id` в content part чата, модель читает содержимое напрямую. **Проверено**: в txt на 95 байт спрятано «фиолетовый слон 42», после вопроса модель ответила дословно |
| 🔍 **Веб-поиск** | У апстрима `feature_config.auto_search` включён по умолчанию; `thinking: auto` + явная просьба — и модель ищет новости за текущий день и прикладывает ссылки на источники |
| ⚡ **Прогрев сессий** | Создание сессии (`chats/new`) по замерам занимает **2,9~3,8 с**. Для «горячих» аккаунтов заранее создаётся по одной пустой сессии (`warm_chats_per_account`, по умолчанию 1), **чистая экономия около 1,2 с на запрос (−18%)**; охват динамически масштабируется вслед за трафиком, использованная сессия тут же пополняется. **Сессия — ресурс уровня аккаунта** (отправка с другого аккаунта даёт `CHAT_NOT_FOUND`), поэтому создаётся и используется по аккаунтам |
| 🔁 **Смена аккаунта при ошибке** | Аккаунт меняется только при сбоях, про которые **можно доказать, что запрос не был принят**: ① однозначные 401 / квота / 429 / риск-контроль; ② **быстрый отказ** (ошибка апстрима не позднее чем через 10 с — работу даже не начинали). **Медленные отказы** (5xx, о которых сообщили через десятки секунд; «таймаут без артефактов» при генерации изображений) **не повторяются** — никакой игры на двойном списании: при таймауте генерации изображения аккаунт лишь уходит на охлаждение на 10 минут, после чего честно возвращается 504 (бюджет уже 300 с, ещё один раунд ожидания = подвесить вызывающую сторону на 10 минут) |
| 🧾 **Настоящий usage** | Входные/выходные/мыслительные токены целиком берутся из апстрима, локальных оценок нет (кроме `count_tokens` — там явно указано, что это оценка) |
| 🖥️ **Веб-консоль** | Встроенная одностраничная (без внешних зависимостей): состояние пула аккаунтов · журнал запросов · время до первого символа / длительность / токены · **отладка в диалоговом окне (текстовый поток / изображение / видео, на каждом раунде видны тело запроса и ответ)** · сброс аккаунта в один клик |
| 🪶 **Без зависимостей** | Только стандартная библиотека Go, статический бинарник `CGO_ENABLED=0` (около 8,8 МБ), мультиархитектурные образы |

## Быстрый старт

```bash
# 1. Конфигурация: впишите Bearer-токен из браузера
cp config.example.json config.json
#    F12 → Network → любой запрос /api/v2 → скопируйте строку из Authorization

# 2. Запуск
go run ./cmd/server -config config.json
#    или docker compose up -d --build

# 3. Проверка
curl -s localhost:8400/readyz
curl -s localhost:8400/v1/chat/completions \
  -H 'Authorization: Bearer sk-example' \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.7-plus","messages":[{"role":"user","content":"你好"}],"stream":true}'
```

Консоль: <http://localhost:8400/panel/> (если настроены `api_keys`, введите ключ в правом верхнем углу).

### Развёртывание в контейнере (образ)

```bash
docker run -d --name qwen2api -p 8400:8400 \
  -v $PWD/data:/app/data \
  -e QWEN2API_CONFIG=/app/data/config.json \
  ghcr.io/rsfree/qwen2api:latest
```

Конфигурацию можно задать двумя способами, на выбор:

| Способ | Как сделать | Когда подходит |
|---|---|---|
| Смонтировать файл конфигурации | `-v $PWD/data:/app/data` + `QWEN2API_CONFIG=/app/data/config.json` (или параметр `-config`) | Много аккаунтов, нужна структурированная конфигурация вроде `pool` |
| Только переменные окружения | Задать только `QWEN2API_ACCOUNTS` / `QWEN2API_API_KEYS`, ничего не монтируя | Управляемые платформы, где конфигурация = секрет |

Три места, где легко споткнуться:

- **Путь к конфигурации нужно указывать явно**. В образе нет `config.json` в текущем каталоге, и конфигурацию не следует класть рядом с `/usr/local/bin`.
  Если не указать, сервис **запустится нормально, но с 0 аккаунтов** (это не ошибка запуска, поэтому заметить сложнее) —
  поэтому первая строка лога запуска — «источник конфигурации: …», смотрите сначала на неё.
- **Внутри контейнера работает непривилегированный пользователь `uid 10001`**. Смонтированный каталог должен быть доступен на запись (`chmod 777` или `chown 10001`),
  иначе `state_file` не запишется, и счётчики квот обнулятся при перезапуске.
- **Монтировать конфигурацию с `:ro` можно, а `data/` — нельзя**: в `state_file` нужно писать.

### Как получить учётные данные (два способа, на выбор)

**A. Email и пароль (проще всего, рекомендуется)**

```json
"accounts": [{ "name": "me", "email": "you@example.com", "password": "пароль открытым текстом" }]
```

При запуске шлюз автоматически делает `POST /api/v2/auths/signin` (пароль передаётся через sha256) → с полученным cookie вызывает
`auth.qwen.ai/api/v2/auths/refresh` → получает `access_token` и использует его как Bearer. При истечении учётных данных автоматически перелогинивается.

**B. Просто вставить токен**

1. Войдите в браузере на <https://chat.qwen.ai>;
2. F12 → Network → откройте любой запрос `/api/v2/...`;
3. Скопируйте `eyJ...` из `Authorization: Bearer eyJ...` и впишите в `accounts[].token`.

> 🔴 **Два вида учётных данных не взаимозаменяемы**: cookie-токен, выданный `signin`, годится только для чтения (`/models` — 200),
> при вызове эндпоинтов записи (`chats/new`, `completions`) будет `Unauthorized`; для эндпоинтов записи нужен
> `access_token`, полученный через `refresh`. В этом репозитории для различения используются префиксы `cookie:` / `bearer:`, а «голый» токен при запуске проходит определение формы.
> Также поддерживается полный cookie jar (содержащий `token=` или `;`).

## API

### `POST /v1/chat/completions`

```bash
curl -N localhost:8400/v1/chat/completions \
  -H 'Authorization: Bearer <key>' -H 'Content-Type: application/json' \
  -d '{
    "model": "qwen3.7-plus",
    "thinking": "auto",
    "stream": true,
    "stream_options": {"include_usage": true},
    "messages": [{"role":"user","content":"用一句话解释量子纠缠"}]
  }'
```

Расширенные поля (если не переданы — используются значения сервера по умолчанию):

| Поле | Значения | Описание |
|---|---|---|
| `thinking` | `auto` / `thinking` / `fast` | Режим мышления; `off`/`none` приводятся к `fast` |
| `reasoning_effort` | `low` / `medium` / `high` | Совместимая запись, отображается на fast / auto / thinking |

`choices[0].message.reasoning_content` в ответе (непотоковый режим) или `delta.reasoning_content` (потоковый режим) —
это сводка «глубокого мышления» из веб-версии.

#### Ввод изображений (мультимодальность)

Достаточно положить сегмент с изображением в `content`, принимаются все три формы записи:

```bash
curl -s localhost:8400/v1/chat/completions \
  -H 'Authorization: Bearer <key>' -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.7-plus","messages":[{"role":"user","content":[
      {"type":"text","text":"这张图是什么颜色？只回答颜色名"},
      {"type":"image_url","image_url":{"url":"data:image/png;base64,iVBORw0KGgo…"}}]}]}'
```

| Запись | Форма | Источник |
|---|---|---|
| `{"type":"image_url","image_url":{"url":"…"}}` | Официальный OpenAI chat; `image_url` как просто строка тоже принимается | chat |
| `{"type":"input_image","image_url":"…"}` | Форма Responses | `/v1/responses` |
| `{"type":"image","source":{"type":"base64","media_type":"image/png","data":"…"}}` | Anthropic; `source.type=url` тоже допускается | `/v1/messages` |

Ссылки принимаются в трёх видах: **URL / data URI / «голый» base64** (то же разрешение ссылок, что и для поля `image` в `/v1/images`;
«голый» base64 определяется по магическим байтам, объявленному типу не доверяем). Не более 20 изображений за раз, при превышении — 400 с указанием на `param=image`.

Путь (`chat_type` по-прежнему **`t2t`**, элементы содержат `file_class=vision`):

| Форма ссылки | Действие шлюза |
|---|---|
| `http(s)://…` | **Как есть** записывается в `files[].url`, апстрим сам забирает изображение. Без скачивания и загрузки |
| `data:image/…;base64,…` / «голый» base64 | После декодирования сохраняется в `BlobStore` в памяти, вместо него подставляется `https://<blob_base_url>/v1/blobs/<32hex>.png` |

`/v1/blobs/<id>` — **безаутентификационный** эндпоинт только для чтения (апстрим при получении изображения не передаёт наш ключ), безопасность обеспечивается
128-битным случайным ID + TTL 2 часа + доступом только на чтение.

> 🔴 **Почему больше не используем загрузку через `getstsToken`** (проверено 30.10.2026): этот эндпоинт
> защищён проверкой на человека от Alibaba Cloud WAF (страница со слайдером, HTTP 200 с HTML внутри). Bearer / Cookie / с bx-ua / без /
> с прогревом acw_tc+x-ap / 14 разных выходов / напрямую — все 9 комбинаций получили проверку; при этом с того же выхода
> `/api/v2/models/` работает нормально. **Но передачи внешней ссылки в `files[].url` вполне достаточно**: по замерам модель точно называет цвет
> чисто красной картинки и читает `HELLO42` с картинки с текстом. Подробности — `docs/UPSTREAM.md` §6.1.
>
> 🔴 Сбой разбора любой ссылки на изображение — это **400**, ни в коем случае не «пропустить эту картинку и продолжить диалог» —
> иначе модель не увидит изображение, но ответит как ни в чём не бывало, и вызывающая сторона решит, что мультимодальность работает.
>
> 📌 `blob_base_url` необходимо настроить на публичный домен (апстрим забирает изображение из собственного дата-центра, внутренний адрес ему недоступен).

### `POST /v1/images/generations`

Набор полей соответствует каноническому виду image-adapter (текст→изображение и изображение→изображение — один эндпоинт, разветвление по `image`):

```bash
curl -s localhost:8400/v1/images/generations \
  -H 'Authorization: Bearer <key>' -H 'Content-Type: application/json' \
  -d '{"prompt":"a cat wearing a beret, flat illustration","size":"16:9"}'
```

```json
{"created":1793185538,"data":[{"url":"https://cdn.qwenlm.ai/output/.../t2i/....png?key=<JWT>"}]}
```

> `url` — это **оригинальная ссылка CDN апстрима**, передаётся как есть: без переписывания, без сохранения на диск, без перезаливки.
> ⚠️ У этой ссылки двойная защита от хотлинкинга — UA + Referer (см. `docs/UPSTREAM.md` §4.5.6): в адресной строке браузера открывается,
> а при загрузке через `<img>` на странице / серверным SDK — 403/404. Для обхода используйте прокси того же шлюза
> `GET /v1/media/<исходный path>` (без аутентификации, прозрачная передача в реальном времени), см. таблицу эксплуатационных эндпоинтов ниже.

| Поле | Описание |
|---|---|
| `prompt` | Обязательно, если нет `image` |
| `image` | `str` или `str[]` (URL / data URI / «голый» base64), не более 20. Непустое значение = **изображение→изображение**: отправляется как `chat_type=image_edit`, референсные изображения так же идут по **прямой передаче URL / локальному blob** (больше не через заблокированный WAF STS). По замерам: белый фон с чёрным `HELLO42` + «фон сделать синим, текст сохранить» ⇒ артефакт 2752×1376, синий фон, чёрный текст (соотношение сторон совпадает с оригиналом — это настоящее редактирование, а не перерисовка) |
| `mask` | Без `image` — 400; вместе с `image` принимается, но не пересылается — у апстрима нет семантики inpaint, **заголовок ответа `X-Qwen2API-Warnings` явно об этом сообщит** |
| `n` | Недопустимые значения приводятся к 1; максимум 4 (каждое изображение — отдельный вызов апстрима + одно списание квоты) |
| `size` | Принимаются `1024x1024` / `1:1` / `auto`, внутри отображаются на 5 вариантов соотношения сторон апстрима; **при приближении с потерями или невозможности отображения — предупреждение в заголовке** (приближение меняет композицию, молча делать это нельзя) |
| `watermark` | Та же семантика, что у видео (нативная для Ark): `true` = сохранить слой Qwen от апстрима; `false` / по умолчанию = удалить водяной знак (контролируется `storage.image_strip_watermark`). Если удаление водяного знака не включено, `false` выполнить невозможно, и это попадёт в заголовок предупреждений |
| `response_format` | `url` (по умолчанию) / `b64_json`; неизвестное значение считается незаданным, ошибки нет |
| `quality` / `style` / `user` | Принимаются, но на апстрим не влияют (в qwen нет таких понятий); `quality` / `style` попадают в заголовок предупреждений, `user` — просто идентификатор, подсказки не выдаём |
| Любые другие ключи | Все нераспознанные поля принимаются и попадают в заголовок предупреждений — у апстрима нет канала для extras, делать вид, что они действуют, нельзя |

> 🔴 **Референсное изображение перед отправкой проверяется на «отрисовываемость»** (data URI / «голый» base64 декодируются полностью один раз):
> не изображение или усечённые пиксельные данные ⇒ **400 `invalid_request_error` (`param=image`)**,
> аккаунт не выбирается, сессия не создаётся, квота не тратится. Проверка отсекает только два случая — «невозможно отрисовать»,
> и **не отсекает дефекты контрольной суммы** — всё, что отрисовывается в macOS ImageIO / браузере, пропускается
> (декодер Go строже, и использовать его как входной фильтр значило бы ошибочно отсекать реально пригодные изображения).
>
> Брешь, обнаруженная 19.11.2026 пробами image-adapter: до исправления из 15 проб бесплатного уровня в 13 запросах с битыми изображениями
> **каждый израсходовал по отдельному аккаунту** (создание сессии + обращение к апстриму), а возвращённые апстримом
> `image_edit_input_unreadable` / `internal_error` оборачивались в `502 повторите позже` —
> клиент лишь повторял попытки с тем же битым изображением. После исправления такие запросы получают 400 локально, **без смены аккаунта и без записи сбоя аккаунту**.

> **`X-Qwen2API-Warnings` на пути изображений действует так же** (общая семантика с видео): значение — несколько URL-кодированных текстов,
> разделённых переводом строки. Он несёт информацию только одного рода — **«получено, но не вступило в силу / деградация с потерями»**.
> Это точка приложения инварианта 2 image-adapter: не 400 (это прервало бы нормальные вызовы) и не молчание (вызывающий решил бы, что параметр сработал).
>
> **`/v1/images/edits` — multipart-вход с тем же набором полей**: `prompt` и `image` (или `image[]`) обязательны,
> `model` / `response_format` / `watermark` передаются обычными полями формы (булевы значения пишутся как `true` / `false`).
> **Политика водяных знаков полностью совпадает с generations**: по умолчанию водяной знак удаляется (при сбое без деградации), слой апстрима сохраняется только при `watermark=true`.
> Раньше edits не делал постобработку, и один модальный режим через два входа выдавал артефакты то с водяным знаком, то без — исправлено.

> 🔴 `prompt` **отправляется апстриму как есть**, не добавляйте от себя обёрток вроде «Пожалуйста, нарисуй картинку:». t2i — явный тип,
> апстрим диспетчеризует по `chat_type`; переписанный prompt заставит его молча вхолостую крутиться (по замерам 200 с без контента).
>
> ⚠️ **Подводные камни со ссылками на артефакты** (проверено, в этом репозитории закрыто):
> 1. **В первые секунды после генерации CDN ещё не завершил перенос** — при немедленной загрузке получите 404 + 226 байт HTML — «мёртвая ссылка».
>    Режим `b64_json` использует повторы с откатом; прокси `/v1/media` при 404 тоже повторяет один раз.
> 2. **У исходной ссылки две защиты от хотлинкинга** — UA вроде `curl/*` блокируется WAF с ответом 404 (тело ответа
>    неотличимо от «ещё не перенесено», очень легко поставить неверный диагноз); с чужим Referer — 403. `url` возвращается как есть, поэтому **при самостоятельной загрузке нужен UA браузера**;
>    если не хочется возиться — используйте прокси `/v1/media`.
> 3. Подлинность определяется по **magic bytes**, а не по `Content-Type` (настоящая картинка может вернуться как `application/octet-stream`);
>    `/v1/media` при `Content-Type`, не являющемся `image/*`, подстраховывается определением по расширению.

### `POST /api/v3/contents/generations/tasks` (нативный протокол Volcano Ark)

Выход видео **дословно соответствует data plane Volcano Ark**: клиент указывает base_url на
`https://qwen2api.1task.cn/api/v3`, и SDK Ark / клиенты протокола Seedance могут подключаться напрямую.

| surface | Метод | Что возвращает |
|---|---|---|
| Создание задачи | `POST /contents/generations/tasks` | `{"id":"cgt-…"}` (**только id**, принято ≠ успешно) |
| Запрос задачи | `GET /contents/generations/tasks/{id}` | Полный объект задачи |
| Запрос списка | `GET /contents/generations/tasks` | `{items[], total}` |
| Отмена / удаление | `DELETE /contents/generations/tasks/{id}` | `200 + {"Result":{}}` |
| Получение ролика | `GET /contents/generations/tasks/{id}/content` | Байты mp4 (**расширение шлюза**, в Ark такого эндпоинта нет) |

```bash
B=https://qwen2api.1task.cn/api/v3/contents/generations/tasks

# Отправка (content[] — единственный носитель входных параметров; возвращается только id)
curl -s $B -H 'Authorization: Bearer <key>' -H 'Content-Type: application/json' \
  -d '{"model":"happyhorse11",
       "content":[{"type":"text","text":"一只橘猫在窗台上打哈欠"}],
       "ratio":"16:9","resolution":"720p","duration":5,"generate_audio":true}'
# → {"id":"cgt-20261108194012-a1b2c3d4"}

# Опрос (?refresh=1 пропускает 2-секундное дросселирование)
curl -s "$B/cgt-20261108194012-a1b2c3d4?refresh=1" -H 'Authorization: Bearer <key>'
# → {"status":"running","content":{"video_url":null},"error":null,
#    "usage":{"completion_tokens":30,"total_tokens":30,"credits":30},…}

# Список (локальный снимок) / удаление (только для конечных состояний)
curl -s "$B?filter.status=succeeded&page_size=20" -H 'Authorization: Bearer <key>'
curl -s -X DELETE "$B/cgt-…" -H 'Authorization: Bearer <key>'

# Получение ролика (рекомендуется: шлюз забирает с UA браузера, обходя блокировку по UA на CDN)
curl -s "$B/cgt-…/content" -H 'Authorization: Bearer <key>' -o out.mp4
```

Параметры списка — как в нативном Ark: `filter.model` / `filter.status` / `filter.task_ids` (повторяющееся имя параметра)
/ `page_num` / `page_size` (оба `[1,500]`, по умолчанию 1 / 20). `total` — **общее число после фильтрации**, а не число записей на странице.

Шесть состояний: `queued` / `running` / `succeeded` / `failed` / `expired` / `cancelled`.
Нераспознанное состояние апстрима **сводится к `running` (нефинальное)** и возвращается вместе с `status_raw`.

| Дисциплина | Почему |
|---|---|
| Ответ на создание **содержит только `id`** | Принято ≠ успешно. Добавлять туда status — значит обещать форму, на которую клиент не должен полагаться |
| `content.video_url` заполнен только при `succeeded` | Выдавать адрес до успеха — значит лгать |
| Параметры через один из двух носителей | Одновременное появление поля body и суффикса prompt (`--rs/--rt/--dur`) — сразу 400 |
| Идемпотентность | Повторная отправка того же намерения (одинаковый отпечаток, нефинальное состояние, в пределах 1 часа) возвращает ту же задачу, **без повторного списания** |
| Соответствие задач сохраняется на диск | `data/videos.json`, хранится 8 дней. Задача апстрима живёт 7 дней, артефакт — 24 ч; хранить только в памяти — значит терять id при перезапуске |
| Колбэки | `callback_url` поддерживается; тело push и ответ на запрос создаются **одним и тем же сериализатором**, идемпотентность по `(id,status)` |

#### 🔴 Известные отличия от нативного Ark (то, что сделать невозможно, — всегда явный 400, без тихой деградации)

| Поведение Ark | Этот шлюз | Причина |
|---|---|---|
| `usage.completion_tokens` — число токенов | **Равно списанным за этот раз кредитам** | Qwen не считает токены, а только списывает кредиты. Дополнительно приведено `usage.credits` с явной пометкой |
| `DELETE` для `queued` → `cancelled` | **400 `InvalidParameter.OperationDenied`** | У апстрима нет эндпоинта отмены. Делать вид, что отменили, — значит клиент решит, что остановлено, а на деле продолжается и тарифицируется |
| ID материалов `asset://` | 400 | У апстрима нет библиотеки материалов |
| `frames` | 400 | Апстрим понимает только `duration` в секундах |
| `duration=-1` (модель выбирает сама) | 400 | Апстрим не поддерживает; длительность напрямую определяет кредиты |
| `duration` — любое значение 4~30 | Только 5 / 10 / 15 | Ступени апстрима |
| `resolution` 480p / 4k | Только 720p / 1080p | Ступени апстрима |
| `ratio` 21:9 | 400 | В 6 вариантах апстрима нет 21:9 |
| `watermark` | **Исполняется слоем хостинга** (см. ниже «Удаление водяных знаков и собственный хостинг»): `false` (значение по умолчанию в Ark) → удаляется постобработкой; `true` → доставляется как есть, слой апстрима сохраняется | Апстрим принудительно добавляет водяной знак, **без какого-либо параметра-переключателя**, возможна только пиксельная постобработка |
| `seed` / `camera_fixed` / `return_last_frame` / `output_format` / `draft` / `service_tier` / `priority` / `tools` | Принимаются, но не действуют, фиксируются в заголовке ответа `X-Qwen2API-Warnings` | У апстрима нет соответствующих параметров |
| `filter.service_tier` | Игнорируется (не фильтрует) | У апстрима нет понятия уровня сервиса |
| Референсное видео / референсное аудио | 400 | `attachments` апстрима принимает только `{type:"image"}` |

#### Названия моделей и псевдонимы

`model` — это **имя маршрута**, а не ID модели апстрима. Порядок разрешения:

1. **Встроенные имена ядер**: `happyhorse11` / `happyhorse` / `wan27`
   (также принимаются записи вроде `HappyHorse 1.1`, `wan-2.7`, регистр и разделители игнорируются)
2. **Псевдонимы из конфигурации**: `config.video.aliases`, `имя клиента → ядро`
3. Ни то ни другое ⇒ считается именем chat-модели, ядром служит `config.video.root_model`

По какому бы пути ни шло разрешение, `model` в ответе **возвращает исходное имя клиента** — клиент, маршрутизирующий по возвращённому имени, не потеряет модель.

```json
"video": {
  "aliases": {
    "doubao-seedance-2-0-pro-260628": "happyhorse11",
    "doubao-seedance-1-0-lite-t2v-250428": "wan27"
  }
}
```

> ⚠️ Псевдоним — лишь **метка маршрута**: артефакт генерируется апстримом этого шлюза и **не имеет отношения к моделям doubao**.
> Настройка `doubao-seedance-*` — это просто знакомое клиентам Ark имя,
> не сопоставляйте его с прайс-листом ByteDance — в notes каждой записи-псевдонима в `/v1/models` это тоже написано.

`/v1/models` перечисляет и записи ядер, и записи псевдонимов; `params.modes` указывает поддерживаемые ядром сценарии
(`t2v` / `first_frame` / `first_last` / `omni_ref`), `params.sizes` — 6 проверенных вариантов соотношения сторон.

### `POST /v1/files` + вопросы по файлу

```bash
# 1) Загрузка
curl -s localhost:8400/v1/files -H 'Authorization: Bearer <key>' \
  -F 'file=@report.pdf' -F 'purpose=assistants'
# → {"id":"file-cfa897…","object":"file","bytes":95,"filename":"report.pdf",…}

# 2) Вопрос (content part ссылается на file_id)
curl -s localhost:8400/v1/chat/completions -H 'Authorization: Bearer <key>' \
  -H 'Content-Type: application/json' -d '{
    "model":"qwen3.7-plus",
    "messages":[{"role":"user","content":[
      {"type":"text","text":"这份文件讲了什么？"},
      {"type":"file","file":{"file_id":"file-cfa897…"}}
    ]}]
  }'
```

У апстрима нет «библиотеки файлов»: файл **путешествует вместе с сообщением** — шлюз сначала на `/v1/files` выполняет загрузку через `getstsToken`,
временно сохраняет элемент `files[]` апстрима, а при вопросе собирает обратно в `messages[0].files` (`chat_type` по-прежнему `t2t`).

> ⚠️ Элемент хранится в памяти только 2 часа и **привязан к аккаунту, который его загрузил** (file_id — ресурс уровня аккаунта).
> После перезапуска процесса старые id `file-…` дают 400.

Текстовые модели берутся у апстрима (TTL 10 минут; если получить не удалось — используется встроенный список, **никогда не 5xx**), модели Agent и генерации добавляет шлюз.

[

  {"id": "qwen3.8-max-agent", "media": "text", "thinking": false, "vision": true},
  {"id": "qwen-image-3.0", "media": "image", "endpoint": "/v1/images/generations",
   "params": {"sizes": ["1:1","4:3","3:4","16:9","9:16"], "max_n": 4}},
  {"id": "happyhorse11",   "media": "video", "endpoint": "/api/v3/contents/generations/tasks",
   "params": {"resolutions": ["720P","1080P"], "durations": [5,10,15],
              "credits": {"720P": {"5": 30, "10": 60, "15": 90}}}}
]
```

### Модели Agent (`qwen3.8-max-agent` / `qwen3.8-flash-agent`)

У режима Agent **независимый список моделей** на стороне апстрима (`GET /api/v2/models/agent_mode`, по замерам только
`qwen3.8-max` и `qwen3.8-flash`), он не пересекается с 7 моделями обычного chat. Поэтому шлюз публикует их через **псевдонимы**,
чтобы `chat_type` для одного и того же id не становился непредсказуемым:

| Что вы пишете в `model` | `model` апстрима | `chat_type` / `sub_chat_type` |
|---|---|---|
| `qwen3.8-max-agent` | `qwen3.8-max` | `agent_mode` / `lite` |
| `qwen3.8-flash-agent` | `qwen3.8-flash` | `agent_mode` / `lite` |
| Любая другая chat-модель | как есть | `t2t` / `t2t` |

- Параметр `thinking` **для Agent не действует**: у апстримного Agent нет режимов «авто/мышление/быстрый», зафиксирован Fast
  (в `feature_config` всего 5 ключей, и нет `auto_search`);
- Мышление идёт через `reasoning_content`, но Agent выдаёт **приращения исходного текста мышления** (обычный режим выдаёт накопительный массив сводок);
- `usage` апстрим кладёт в `extra.model_service_info` (на верхнем уровне всегда пусто), шлюз читает оттуда как запасной вариант
  и берёт `task_usage` (накопленное за всю задачу, включая каждый раунд инструментов);
- 🤝 **Липкость диалога (включена по умолчанию)**: несколько раундов одного диалога **переиспользуют сессию апстрима** и полностью используют prompt cache —
  по замерам в рамках одного `chat_id` системный prompt агента в ~14k токенов оплачивается полностью только в первом раунде, затем 13k+ попадают в кэш.
  Ключ диалога определяется по трём приоритетам: заголовок `X-Dialog-Id` → поле `user` → **`hash(model + весь system + первое сообщение пользователя)`**
  (запасной вариант без доработок клиента; якорем берётся весь текст, а не префикс; system участвует, чтобы разделять разные приложения).
  Параметр конфигурации `dialog_sticky` (по умолчанию true), при отключении возвращается режим «новая сессия на каждый запрос».
- 🔴 **Липкость лишь экономит деньги и не отвечает за контекст**: историю по-прежнему каждый раунд присылает клиент, полностью в `messages`,
    а мы сплющиваем её в prompt, что и гарантирует контекст. Поэтому, если получить сессию не удалось (конкурентность/смена аккаунта/перезапуск), всегда **берётся новый аккаунт и открывается новая сессия**,
    никогда не блокируем и никогда не отвечаем 409 — цена лишь один промах кэша.
- ⚠️ Конкурентные запросы в один и тот же диалог: **автоматическая деградация к новому аккаунту и новой сессии** (конкурентность на одном `parentId` приводит к ветвлению цепочки диалога у апстрима).
    `dlg=hit` / `dlg=new` в журнале — это показатели наблюдаемости этого механизма.
- 🔴 **Слот конкурентности агента уровня аккаунта у апстрима всего один** (по замерам `user.too_many_concurrent`):
    второй раунд, отправленный сразу следом, будет отклонён. Шлюз поступает так: «ждёт 1,2 с и повторяет на том же аккаунте, чтобы сохранить кэш → если всё ещё занято, меняет аккаунт»,
    и это «подождите» не превращается напрямую в 502.
- 📈 Замеренный выигрыш: второй раунд того же диалога **11,2 с → 2,4 с** (`dlg=hit` + `chat=cached`).
- 🛡️ **Короткая первая фраза не «липнет»**: если первое сообщение пользователя короче 8 символов («你好»/«1»/«继续»), запасной вариант с hash **не включается** —
  такие фразы в реальном трафике крайне часто повторяются, коллизия ключа склеила бы два несвязанных диалога в один (ответ невпопад + утечка контекста).
  Хотите липкость и для коротких фраз — явно передавайте `X-Dialog-Id` или `user`, для этих двух уровней длина не ограничена.

🔴 **У апстрима нет отдельных id моделей для изображений/видео** — замер 30.10.2026: `GET /api/v2/models/` содержит только
7 chat-моделей; для изображений ядро выбирается через `extra.meta.model` (`qwen-image-3.0`), для видео — через
`biz_data.rootModel` (`happyhorse11`). Поэтому две эти записи в списке — **имена моделей самого шлюза**, шлюз переводит их в те два поля апстрима:

| Что вы пишете в `model` | chat-модель для создания сессии | Ядро генерации |
|---|---|---|
| Не указано / текстовая модель вроде `qwen3.7-plus` | та, что вы указали | Значение из конфигурации (`image_model` / `root_model`) |
| `qwen-image-3.0` (или `Qwen-Image 3.0`) | Текстовая модель по умолчанию | `qwen-image-3.0` |
| `happyhorse11` (или `HappyHorse 1.1`) | Текстовая модель по умолчанию | `happyhorse11` |

- Сравнение имён **игнорирует регистр, пробелы и разделители**: названия `Qwen-Image 3.0` /
  `HappyHorse 1.1`, показанные в UI апстрима, можно копировать как есть;
- Вызов `/v1/chat/completions` с моделью генерации даёт **400 с указанием верного пути** («используйте /v1/images/generations»),
  вместо того чтобы отдавать апстриму имя модели и получать в ответ непонятный `Bad_Request`;
- `endpoint` / `params` — **аддитивные расширенные поля**, клиенты, берущие только `id/object/created/owned_by`,
  работают как обычно.

### `POST /v1/messages` (Anthropic)

Клиентам вроде Claude Code / Cline достаточно указать Base URL на этот сервис. Ответ записывается по последовательности событий Anthropic
(`message_start` → `content_block_delta` → `message_delta` → `message_stop`).

> Блок `thinking` не создаётся: thinking у Anthropic требует подписи, а шлюз подписи не подделывает.

### `POST /v1/responses`

Для подключения клиентов вроде Codex, понимающих только Responses. Поддерживаются и текст, и вызовы клиентских функций: `tools` проходят через тот же перевод, что и в
chat, выдаются элементы вывода `function_call`; передаваемые обратно элементы `function_call` / `function_call_output`
рендерятся в prompt (см. раздел «Вызов инструментов»). Встроенный поиск (`web_search` и т. п.) по-прежнему не поддерживается.

### Как работает вызов инструментов (`tools`)

У апстрима нет канала вызова функций, поэтому этот слой — **трансляция протокола**: клиентские инструменты превращаются в системную договорённость,
а JSON из вывода модели разбирается обратно в структуру, которую клиент может выполнить.

Вход (запрос):

```
POST /v1/chat/completions
{
  "model": "qwen3.8-omni-flash",
  "messages": [{"role": "user", "content": "北京天气如何？"}],
  "tools": [{"type": "function", "function": {
    "name": "get_weather",
    "description": "查询指定城市的实时天气",
    "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}
  }}],
  "tool_choice": "auto"          // auto / none / required / {"type":"function","function":{"name":"…"}}
}
```

В конец prompt шлюз добавляет блок протокола (содержимое примерно такое):

```
【工具调用协议 · 由网关注入，优先于其它指令】
可用工具：
1. get_weather — 查询指定城市的实时天气
   参数 Schema：{"properties":{"city":{"type":"string"}},"required":["city"],"type":"object"}
输出规则（严格遵守，违反会导致客户端解析失败）：
- 需要工具结果才能回答时：整条回复只输出一个 JSON 对象（可用 json 代码块包裹）
  {"tool_calls":[{"name":"工具名","arguments":{参数对象}}]}
- 不需要工具时：直接用自然语言回答，不要输出上述 JSON
```

(Перевод блока протокола: «【Протокол вызова инструментов · внедряется шлюзом, приоритетнее остальных инструкций】 Доступные инструменты: … Правила вывода (соблюдать строго, нарушение приведёт к сбою разбора на клиенте): — если для ответа нужен результат инструмента: весь ответ — только один JSON-объект (можно обернуть в блок кода json) …; — если инструмент не нужен: отвечать обычным естественным языком, не выводя указанный JSON». Сам текст протокола отправляется модели на китайском, как показано выше.)

Выход (ответ; каждый из трёх входов отвечает по собственному протоколу):

| Вход | Форма вызова инструмента | Завершающая метка |
|---|---|---|
| `/v1/chat/completions` | `message.tool_calls[]` (в потоке — `delta.tool_calls[]`, накапливаются по `index`) | `finish_reason: "tool_calls"` |
| `/v1/messages` | `type:"tool_use"` в `content[]` (в потоке `input_json_delta`) | `stop_reason: "tool_use"` |
| `/v1/responses` | `type:"function_call"` в `output[]` (в потоке три события: added / arguments.delta / arguments.done) | `status: "completed"` |

Многораундовая передача: клиент на втором раунде присылает `assistant.tool_calls` + `role:"tool"` (у Anthropic —
`tool_use` + `tool_result`, у Responses — `function_call` + `function_call_output`),
шлюз рендерит их как «\n[вызов инструмента] get_weather({"city":"北京"})\nрезультат инструмента: get_weather → {…}»,
и сопоставляет результат с вызовом по `tool_call_id` (поэтому результат не перепутается с другим инструментом).

Границы (прямо записаны здесь, чтобы избежать неверных выводов):

| Ситуация | Поведение |
|---|---|
| Модель выводит не по протоколу (сначала любезности, потом JSON) | Весь текст возвращается как обычный, `finish_reason=stop` — лучше пусть клиент увидит JSON-текст, чем подделывать вызов |
| Выдуманное имя инструмента (нет в `tools` этого раунда) | То же самое, разбор прямо признаётся неудачным (иначе клиент пойдёт выполнять несуществующую функцию) |
| `arguments` — не JSON-объект | То же самое (чтобы не передавать исполнителю клиента испорченные параметры) |
| `tool_choice: "none"` | Блок протокола не внедряется, на этом раунде идёт обычный диалог (одновременно выдаётся заголовок предупреждения) |
| На сервере `tool_calls.enabled=false` | `tools` игнорируются, идёт обычный диалог, и заголовок предупреждения сообщает, что не вступило в силу |
| Модель `*-agent` с `tools` | Деградация к базовой обычной модели. По замерам `qwen3.8-flash-agent`, получив `get_weather`, отвечает «у меня нет такого инструмента», а затем компенсирует **собственным веб-поиском** — клиентский инструмент никогда не срабатывает, а результат выглядит завершённым (отлаживать сложнее, чем ошибку) |
| Число инструментов за раунд / объём schema | Бюджет по умолчанию 256 штук / 32 КБ (`tool_calls.max_tools` / `max_schema_bytes`). **При превышении — только деградация**: на этом раунде эмуляция инструментов пропускается, модель работает как есть (agent остаётся agent), и в заголовке предупреждений это указывается — **400 не возвращается**. 400 только за **недопустимые/повторяющиеся имена** (это баг клиента) |

### Семантика ошибок (что видит клиент)

| Ситуация | HTTP | `error.type` | `error.code` | `message` |
|---|---|---|---|---|
| Ключ API отсутствует / недействителен | **401** | `authentication_error` | `AuthenticationError` | `无效的 API Key` («Недействительный API Key») |
| Апстрим 180 с шлёт только heartbeat, без артефактов | **504** | `upstream_timeout` | — | `upstream timeout, please retry later` |
| Апстрим 5xx / сбой передачи / несоответствие формы | **502** | `upstream_error` | — | `upstream error, please retry later` |
| Нет доступных аккаунтов (все на охлаждении/недействительны) | **503** | `service_unavailable` | — | `no available upstream account, please retry later` |
| Учётные данные апстрима испорчены (на стороне шлюза) | 502 | `upstream_error` | — | `upstream authentication failed` |
| Квота/лимит | 429 | `insufficient_quota` / `rate_limit_error` | — | Конкретно — «какая квота, сколько не хватает» (на китайском) |
| Риск-контроль апстрима (`RGV587` / страница WAF) | **429** + `Retry-After: 30` | `rate_limit_error` | — | `upstream rate limited, please retry later` |
| Ошибка в параметрах | 4xx | `invalid_request_error` | см. ниже | Конкретно — до поля (на китайском) |

> 📌 `error.code` использует **словарь Ark** и разделяет роли с `error.type`:
> `type` решает «нужно ли повторять», `code` решает «нужно ли менять параметры».
>
> | `code` | Ситуация |
> |---|---|
> | `AuthenticationError` | 401 — **все эндпоинты** (аутентификация — сквозная ошибка, единообразно формируется в `wrap`) |
> | `MissingParameter` | Видео: нет `content` / `model` |
> | `InvalidParameter` | Видео: неверный формат значения |
> | `InvalidParameter.UnsupportedParameter` | Видео: у апстрима нет такой возможности (первый+последний кадр при смене ядра, соотношение сторон, длительность, разрешение) |
> | `InvalidParameter.TaskTypeConstraint` | Видео: смешивание первого/последнего кадра с референсными изображениями |
> | `InvalidParameter.OperationDenied` | Видео: DELETE для нефинального состояния (у апстрима нет эндпоинта отмены) |
> | `ResourceNotFound` | Видео: неизвестный id задачи |
>
> Для ошибок параметров в chat / images / messages сейчас указывается только `type` (`code` в OpenAI по определению nullable),
> только 401 общий для обеих сторон — он обязан нести код, иначе клиент Ark, ветвящийся по `code`, получит пустое значение.

> Почему риск-контроль — это 429, а не 502: 502 клиент воспримет как «шлюз сломан» и немедленно повторит запрос, что удлиняет окно риск-контроля
> (прод 20.11.2026: все 23 сбоя — это `RGV587`, усиленные повторами). Только 429 + `Retry-After` является
> сигналом, запускающим автоматический откат в SDK / промежуточных шлюзах.

**5xx — всегда короткий английский текст + стабильный type** (клиентам/SDK нужна машиночитаемость, а не руководство по диагностике);
суждения вроде «квота на исходе или апстрим глючит / рекомендуется сменить аккаунт» попадают только в **журнал запросов и логи контейнера**,
на странице «Логи» панели они по-прежнему видны — информация не теряется, просто не утекает наружу. 429 и 4xx сохраняют конкретный китайский текст,
потому что там информация (сколько кредитов не хватает, какое поле превысило лимит) действительно полезна вызывающей стороне.

| **Использование** | Накопленное число запросов, доля успехов, токены, среднее время; журнал запросов (последние 80, с **аккаунтом и IP выхода**) + распределение по моделям/по аккаунтам |
| **Ёмкость** | Сколько изображений ещё осталось сгенерировать каждому аккаунту сегодня, пересчёт остатка в «сколько роликов 720P 5с / 1080P 15с можно сделать», **время ежедневного бонусного начисления** (при наведении видно ожидаемое следующее), а также суммарные значения по всему пулу |
| **Модели и отладка** | Список моделей (с пометками возможностей) + онлайн-отладка (текстовый поток / изображение / видео; для изображений можно подложить **несколько референсных изображений**, до 20 штук, суммарно 16 МБ, отправляются по порядку номеров) |
| **Конфигурация** | **Редактируемая форма + горячее обновление** (20 полей, разделены на базовые/пул аккаунтов/видео/апстрим; при сохранении записывается обратно в config.json и **немедленно заменяет снимок времени выполнения**, кроме пунктов с пометкой «нужен перезапуск»), а также сводка действующей конфигурации только для чтения (сервис/апстрим/квоты/цены видео/источник списка аккаунтов) |

### Вход (сначала ключ, отдельно от токенов `/v1`)

Панель умеет импортировать/удалять аккаунты и видеть все email — поэтому у неё свои учётные данные, по умолчанию это **один ключ**:

```json
"panel": {
  "key": "sk-example",
  "session_hours": 720,
  "session_secret": "при многорепликовом развёртывании обязательно задать одинаковый"
}
```

Соглашение об именовании: и ключ панели, и токен входа формируются как **`sk-` + домен второго уровня** — просто склеиваются, без префиксов и суффиксов
(например, `foo.1task.cn` → `sk-foo`).

Откройте `/panel/` — сразу увидите «Введите ключ для входа»:

- Введите `panel.key` (можно и через переменную окружения `QWEN2API_PANEL_KEY`); **если не задан — принимается любой из `api_keys`**,
  при развёртывании с одним ключом после обновления менять конфигурацию не нужно;
- 🔴 **Если заданы `password` / `password_hash`, принимается только логин и пароль**: токены входа в панель больше не пускают —
  токен инференса по соглашению угадываем, и ему не следует одновременно давать права «удалять аккаунты / видеть все email / отзывать ключи»;
- После отправки сервер меняет его на **подписанный cookie с HttpOnly + SameSite=Lax** (HMAC-SHA256),
  ключ открытым текстом **в localStorage не сохраняется** (старая версия сохраняла, а это значит отдать долгосрочные учётные данные XSS);
- Сессия по умолчанию **30 дней** (настраивается `panel.session_hours`); если ключ подписи пуст, он **выводится из учётных данных**,
  поэтому **перезапуск/выпуск версии не выкидывает из системы** (если задан `session_secret`, приоритет у него — для ротации);
- Глубокая ссылка `?key=…` сначала обменивается на сессию, затем параметр стирается из адресной строки;
- Скрипты / CI по-прежнему могут вызывать `/panel/api/*` напрямую с `Authorization: Bearer <key>`, `x-api-key` или `?key=`
  (если настроены логин и пароль — принимается только `panel.key`, токены входа не принимаются);
- 🔴 **Ключ панели действует только в панели, `/v1` его не принимает** — панель умеет удалять аккаунты, граница прав должна быть чёткой;
  если записать **то же значение** и в `api_keys`, получится один ключ, работающий в обоих местах: стоит токену инференса уйти наружу — и панель тоже открыта.
  Так рекомендуется делать, только если панель не выставлена в публичную сеть (доступ только через туннель / 404 на уровне входа);
- 10 неудачных попыток подряд → блокировка этого IP на 10 минут (панель в публичной сети, без этого барьера открыт перебор).

Хотите всё-таки логин и пароль? Задайте `password_hash` (`qwen2api -passwd 'ваш пароль'`, чтобы не считать число итераций вручную) или
`password` / `QWEN2API_PANEL_PASSWORD` — в окне входа появится ссылка «войти по логину и паролю»;
**если не задано ни то, ни другое** = панель не требует входа (рекомендуется только для localhost/внутренней сети).

> Сессия привязана к имени пользователя: смена имени пользователя (или `session_secret`) аннулирует все сессии;
> флаг `Secure` добавляется автоматически по `X-Forwarded-Proto` (если TLS терминирует nginx, на него приходится полагаться).

### Импорт аккаунтов

Кнопка «Импорт аккаунтов» в правом верхнем углу, три способа:

```
Вставить текст: в каждой строке «email пароль [имя аккаунта] [примечание]»
                разделители: пробел / запятая / вертикальная черта / табуляция, также принимается ----
Импорт файла:   .txt или .json (содержимое попадёт в текстовое поле, можно сверить перед импортом)
Один аккаунт:   форма
```

Также можно просто вставить массив JSON:

```json
[{"name":"main","email":"a@b.com","password":"pw","note":"Go 套餐"}]
```

По умолчанию аккаунты **проверяются входом по одному**, и только потом попадают в пул — без проверки в пул насыпаются «глухие патроны»: аккаунт с неверным паролем
будет выбран, запрос завершится неудачей, потом охлаждение, а выглядеть это будет как сбой апстрима. Для строк, не прошедших проверку, построчно указывается причина (`邮箱或密码错误` («неверный email или пароль») /
`被上游风控拦截` («заблокирован риск-контролем апстрима») / `登录超时` («тайм-аут входа»)), в хранилище попадают только успешные.

### Где хранится список аккаунтов (важно)

```
config.json          декларативная база (при развёртывании монтируется только для чтения)
data/accounts.json   под управлением панели (импорт/удаление пишут сюда; **если файл существует — он полностью берёт управление на себя**)
```

Не записывать обратно прямо в `config.json` есть две причины: при развёртывании он смонтирован как `:ro`; а кроме того, позволить программе менять декларативную
конфигурацию пользователя слишком рискованно (один баг формата может испортить заодно `pool` и `video`).

«Полностью берёт управление на себя», а не «слияние» — это сделано намеренно: при слиянии «удалённый аккаунт после перезапуска возвращается».
Хотите вернуться к декларативной конфигурации — удалите `accounts.json` и перезапустите.

> Права на файл `0600`, атомарная запись (временный файл в том же каталоге + rename). Внутри пароли открытым текстом, не коммитьте в репозиторий:
> `.gitignore` в каталоге развёртывания его уже исключает.

### Опрос и издержки

Фронтенд раз в 5 с запрашивает `/panel/api/overview`; обновление баланса идёт с **TTL 2 минуты**, так что опрос не
«разогревает» домен кредитов апстрима. Ручное нажатие «Обновить баланс» TTL игнорирует.

### Прогрев сессий (экономим 2 секунды в начале запроса)

`POST /api/v2/chats/new` по замерам занимает **2,9~3,8 с** (при долгоживущем соединении шлюза, см. `build_ms_avg`),
то есть больше половины времени диалога. Поэтому шлюз **заранее создаёт по одной пустой сессии для «горячих» аккаунтов**:

| Пункт | Описание |
|---|---|
| Охват | Того же происхождения, что и прогрев access token: `warmTarget` (оценивается по трафику за последние 10 минут), размер одного прохода `warmBatch` масштабируется вместе с ним |
| Пополняется только `t2t` | Диалоги составляют подавляющее большинство запросов; t2i / image_edit / t2v занимают по 50~90 с, доля 2,4 с пренебрежимо мала |
| Использовали — пополнили | Берётся и сразу удаляется (после отправки в сессии появляются сообщения, и повторное использование превратилось бы в многораундовый диалог), и тут же асинхронно пополняется |
| Предел кэша | `chat_pool_ttl_s` (по умолчанию 900 с) — есть ли у апстрима истечение пустых сессий, замерами не подтверждено, консервативно берётся тот же порядок, что и у access |
| Отключение | `warm_chats_per_account: 0` |

> 🔴 **Сессия — ресурс уровня аккаунта**: chat, созданный аккаунтом A, при отправке с аккаунта B даёт `CHAT_NOT_FOUND` («этот диалог удалён»,
> проверено). Поэтому пул группируется по `(аккаунт, тип сессии)` и прогревать можно только «аккаунты, которые вот-вот будут использованы» (`pool.HotNames`).
>
> Наблюдаемость: `keepalive.chats = {per, ttl_s, ready, hit, miss, hit_pct, build_ms_avg}` в `/stats`;
> в журнале `chat=cached` (попадание) / `chat=3087ms` (создана заново).

#### Замеренный выигрыш: чистая экономия около 1,2 с (−18%), а не «сэкономлены все 3 секунды»

Сравнение на одной и той же партии запросов, переключался только `warm_chats_per_account` (по 10~11 прогонов, однораундовый диалог):

| | Среднее общее время | Создание сессии | Отправка + чтение потока |
|---|---|---|---|
| Предсоздание выключено (всё создаётся на месте) | **6674 мс** | 3221 мс | 3453 мс |
| Предсоздание включено (попадание) | **5497 мс** | 0 | 5497 мс |

⇒ **Чистая экономия 1177 мс (−18%)**. Обратите внимание: при попадании «отправка + чтение потока» занимает на ~2 секунды больше —
апстриму приходится заново загружать контекст «сессии, созданной несколько минут назад и всё это время пустовавшей», поэтому 2 из сэкономленных 3,2 с возвращаются обратно.
Это объясняет, почему взгляд только на «создание сессии 3 секунды» завышает выигрыш: **реальный выигрыш — только чистая разница**.

### Горячее обновление конфигурации (меняете в панели — действует сразу)

Страница «Конфигурация» в панели — это **форма**, поля передаются бэкендом из `config.Fields` (**белый список**: перечислены только 20 пунктов,
которые безопасно менять). При сохранении:

1. Читается исходный `config.json` (сохраняются ключи-комментарии `// …` и все не отправленные поля)
2. Проверка по типу/диапазону поля (`pool.max_rotate` принимает только 1~10, перечисления — только перечисленные значения, неизвестные ключи отклоняются сразу)
3. Атомарная запись обратно через `tmp + rename`
4. **Целиком заменяется снимок времени выполнения** → лимиты пула аккаунтов/охлаждение/параметры пула сессий вступают в силу немедленно, без перезапуска

Способ вступления в силу:

| Тип | Поля | Вступление в силу |
|---|---|---|
| Все параметры pool | `max_rotate` / `cooldown_*` / `max_inflight_per_account` / `max_image_per_day` / `max_video_*` / `warm_chats_per_account` / `chat_pool_ttl_s` | **Немедленно** |
| Модели и переключатели | `default_model` / `default_thinking` / `expose_reasoning` / `image_model` / `blob_base_url` | **Немедленно** |
| Бюджет генерации изображений | `image_timeout_s` (одна попытка, по умолчанию 300 с) | **Немедленно** |
| Видео | `root_model` / `resolution` / `duration` / `size` | **Немедленно** |
| Определение выхода | `upstream.egress_ip_url` | **Немедленно** |
| Тайм-аут апстрима | `upstream.timeout_s` | Нужен перезапуск (HTTP-клиент создаётся при запуске) |

🔴 **То, чего нет в белом списке, из панели менять нельзя никогда**: `listen` / `state_file` / `api_keys` / `panel.*` /
`upstream.base_url` / `accounts` — это либо ресурсы времени запуска (горячее обновление стёрло бы весь пул аккаунтов),
либо поля, ошибка в которых заблокирует сервис. Их можно менять только правкой файла + перезапуском, в панели это указано явно.

> Если `-config` не передан (развёртывание только на переменных окружения), форма доступна только для чтения, сохранение возвращает 400 с объяснением причины.
> Ключи `// описание` в файле конфигурации сохраняются как есть (читаются в `map[string]any` и записываются обратно).

**Требования к развёртыванию (иначе сохранение в панели завершится ошибкой)**:

| Симптом | Причина | Что делать |
|---|---|---|
| `read-only file system` | В compose смонтировано `./config.json:/app/config.json:ro` | Уберите `:ro` (если хотите оставить только чтение — не меняйте конфигурацию через панель) |
| `rename ... device or resource busy` | Монтирование одиночного файла не позволяет заменить inode | Шлюз автоматически деградирует до «резервная копия + запись поверх», в лог пишется одна строка |

> При записи поверх при монтировании одиночного файла **атомарности нет**: перед записью сначала сохраняется `config.json.bak`,
> если всё же что-то испортилось — восстановите из неё (`cp config.json.bak config.json` и перезапуск). Монтирование каталога по-прежнему работает через tmp+rename.

### Стратегия выбора аккаунта: приоритет аккаунтам, у которых «токен ещё жив»

TTL access token в пуле всего **15 минут**, а держать «горячими» 3000+ аккаунтов невозможно. Поэтому выбор аккаунта
(`Pick` / `PickForImage` / `PickForVideo`) сортирует в таком порядке:

1. Сначала те, у кого **токен ещё жив** (остаток > 2 минут) — иначе каждому запросу придётся лишний раз делать refresh
   или получать 401 и продлевать, впустую теряя сотни миллисекунд;
2. Затем с наименьшим `served` (нагрузка выравнивается по пулу);
3. Затем с наименьшим числом запросов в обработке, дольше всех не использовавшиеся.

Поддерживающий прогрев и выбор аккаунта **имеют общий источник**: живые аккаунты «чем скорее истекают, тем раньше продлеваются» поддерживаются
в тёплом состоянии (если их не продлевать, они истекут прямо под трафиком, и продление ляжет на путь запроса); если живых не хватает до `warmTarget`, добираются
истёкшие по возрастанию `served` — именно они пойдут в работу следующими. Если истекли все аккаунты пула, сортировка не зависает (приоритет ≠ фильтр).

## Прокси выхода (по одному фиксированному IP на аккаунт)

Если все аккаунты входят/запрашивают с одного IP, **признание одного аккаунта рискованным затрагивает весь пул** — апстрим строит профиль по IP выхода.
Поэтому поддерживается стабильное отображение «аккаунт → фиксированный выход» (не случайная ротация — ротация, наоборот, чаще роняет состояние входа):

```json
"upstream": {
  "proxy": {
    "enabled": true,
    "url_template": "socks5h://poolclient-{account}:{password}@pool.livetest.cn:2090",
    "password": "по необходимости (или через QWEN2API_PROXY_PASSWORD)"
  }
}
```

- `{account}` заменяется на имя аккаунта (`main` → `poolclient-main`), `{password}` берётся из поля Password;
- **Поддерживаются только `socks5` / `socks5h`**: нам нужна «смена IP выхода», а HTTP CONNECT-прокси часто добавляют
  `X-Forwarded-For` и изоляции не дают, поэтому они прямо отвергаются;
- Семантика `socks5h` = разрешение доменных имён отдаётся прокси (удалённый DNS). SOCKS5-клиент этого репозитория для доменов всегда использует
  `ATYP=domain`, поэтому не возникает скрытого сбоя вида «локально разрешилось в IP не того региона, соединение есть, но попало под риск-контроль»;
- На каждый аккаунт — один `http.Transport` (переиспользование соединений + стабильный выход), **кэшируется по аккаунту**, не меняется вместе с токеном
  (смена токена не должна менять IP);
- Вход (signin / refresh), загрузка, генерация, чтение баланса — **всё** идёт через выход этого аккаунта — несовпадение IP входа и IP использования
  само по себе является подозрительным сигналом в профиле риск-контроля.

### Что делать с запросами без привязки к аккаунту

У публичных эндпоинтов (проба без входа) нет контекста аккаунта:

| `direct_when_missing` | Поведение |
|---|---|
| `true` (по умолчанию) | Прямое соединение. Подходит для развёртываний, где «прокси — опция» |
| `false` | Прямой отказ. Подходит для развёртываний, где «реальный IP ни в коем случае не должен появляться у апстрима» |

### Как посмотреть IP выхода (по замерам, не на глаз)

Хост прокси у всех аккаунтов один и тот же (`pool.livetest.cn:2090`), **IP выхода назначается на стороне оператора по аккаунтам**,
по одной лишь конфигурации не видно, откуда именно вышел запрос. Поэтому шлюз делает «ленивое определение»:

- Когда аккаунт впервые используется для запроса, в фоне **из его туннеля** выполняется один запрос на `upstream.egress_ip_url`
  (по умолчанию `https://api.ipify.org`, можно заменить, значение `"-"` отключает), IP источника, который увидела другая сторона, сохраняется в пуле;
- Кэш **30 минут**, по истечении следующий запрос заодно перепроверяет; всё время **асинхронно**, не занимает задержку основной цепочки;
- Результат попадает в два места: `egress_ip` в журнале запросов (панель «Логи» → источник/выход, копирование/экспорт тоже включают его),
  и `egress_ip` в снимке аккаунта (виден в `/stats`).

> Диагностический критерий: `client_ip` — это «кто вызывает нас», `egress_ip` — «с какого IP мы обращаемся к апстриму».
> Если одна и та же ошибка апстрима стабильно воспроизводится только на определённом `egress_ip` — проблема в профиле IP, а не в аккаунте.

### Замер (30.10.2026)

Один и тот же пул прокси, разные имена аккаунтов → разные и стабильные выходы:

```
probe-a → 38.6.213.75   (оба раза один и тот же)
probe-b → 38.6.213.41

## Тарификация видео по кредитам (баланс — единственный достоверный критерий)

Видео у апстрима тарифицируется **в кредитах**, а не одной ценой: 720P 5с и 1080P 15с отличаются в 4 раза.

### Цены (два набора по версии модели)

| Ступень | `happyhorse11` (по умолчанию) | `happyhorse` 1.0 |
|---|---|---|
| 720P 5с / 10с / 15с | **30 / 60 / 90** | 40 / 80 / 120 |
| 1080P 5с / 10с / 15с | **40 / 80 / 120** | 70 / 140 / 210 |

- Официальный источник: `GET /api/v2/credits/pricing` (в `scene` `hh11*` — новая версия, `hh*` — старая);
- Сверка по замерам: в счёте `HappyHorse1.1.720P.5s = -30`, `1080P.15s = -120`, что совпадает с таблицей hh11;
- Ступень, цену которой узнать не удалось, — сразу **400**, цену не угадываем (лучше отказать, чем пропустить по неверной цене).

### Баланс: читаем напрямую из учётной книги аккаунта, не гадаем по конфигурации

Шлюз читает **реальный баланс аккаунта** (`sg-entitlement.qwen.com`, см. `docs/UPSTREAM.md` §4.10):

```
GET /stats → pool[].credit_balance = 280, credit_known = true
```

При выборе аккаунта фильтрация идёт по условию «баланс ≥ необходимого на этот раз». Это решает реальную проблему: «обычные» аккаунты с одинаковым названием
могут иметь баланс 40 (только сегодня начислили), 10 (остаток со вчера), 270 (подписка) — зашить в конфигурацию одно число неизбежно неверно.

```
баланс 10  + запрос 720P 5с (30)  → 429 «Недостаточно кредитов на аккаунте: на этот раз нужно 30 кредитов, балансы аккаунтов main=10»
баланс 280 + запрос 720P 5с (30)  → 200, списано 30, баланс сразу становится 250 (оптимистичное списание, не ждём следующего обновления)
```

- Кэш баланса **60 с** (путь видео) / **2 минуты** (опрос панелью `/stats`), одновременно выполняется только один раунд обновления;
- Баланс прочитать не удалось ⇒ **не блокируем**, подстраховывает `insufficient_quota` от апстрима (один сбой интерфейса не должен останавливать возможность генерации видео);
- После успешной отправки сразу **оптимистичное списание**, чтобы второй запрос в ту же минуту не увидел устаревший баланс.

### Конфигурация

```json
"pool": { "max_video_per_day": 1, "max_video_credits_per_day": 0 },
"video": {
  "root_model": "happyhorse11",
  "pricing": { "720P": { "5": 30, "10": 60, "15": 90 },
               "1080P": { "5": 40, "10": 80, "15": 120 } }
}
```

`max_video_credits_per_day` по умолчанию **0 (выключено)**: баланс уже является достоверным критерием, а ещё один слой
«40 очков в день» заблокировал бы 270 очков аккаунта с подпиской. Нужен дополнительный дневной лимит — укажите положительное число.

### Удаление водяных знаков и собственный хостинг (`storage`)

У **видео и изображений** в правом нижнем углу вжат слой Qwen, масштабируемый пропорционально **18,5% короткой стороны**
(720 → 133×33; 960 → 180×47; 1536 → 285×77; 2048 → 382×102),
а прямая ссылка CDN **истекает уже через 24 часа**.

⚠️ Раньше считалось, что это «слой фиксированного размера 133×33 пикселя», потому что у первых трёх образцов короткая сторона как раз была 720;
образец изображения 2752×1536 прямо это опроверг. Якорь — правый нижний угол, размер зависит от короткой стороны.

После включения `storage` цепочка становится такой:

```
апстрим succeeded ──► polishing (внутреннее состояние) ──► удаление водяного знака ──► загрузка ──► succeeded + собственный URL
                          │
                          └─► наружу всегда сообщается running (прямая ссылка с водяным знаком никогда не выдаётся раньше времени)
```

Три дисциплины:

| Дисциплина | Почему |
|---|---|
| Пока не обработано — URL не выдаём | Версия с водяным знаком через 24 ч даёт 404, возможности исправить задним числом нет |
| `polishing` наружу отображается как `running` | В Ark всего шесть состояний, выдуманное состояние приведёт к тому, что клиенты, жёстко написанные по автомату состояний, никогда не дождутся финального |
| При сбое **не** деградируем до прямой ссылки апстрима | Чем отдавать бракованный продукт, который истечёт и с водяным знаком, лучше явно сообщить о сбое |

**Выравнивание с семантикой поля `watermark` в Ark** (это легко перепутать):

В нативном Ark `watermark` по умолчанию **false = без водяного знака**, а наш апстрим добавляет его **принудительно**.
Поэтому шлюз реализует это как «политику доставки», а не как «передаваемый параметр»:

| Клиент передаёт | Что происходит на деле |
|---|---|
| Не передаёт (по умолчанию false) | Водяной знак удаляется |
| `watermark: false` | Водяной знак удаляется |
| `watermark: true` / `--wm true` | **Водяной знак не удаляется**, слой Qwen апстрима доставляется как есть |

Если хостинг не включён, `watermark: false` выполнить невозможно — ответ на создание явно сообщит в
`X-Qwen2API-Warnings`, что «ролик всё ещё с водяным знаком», и не будет делать вид, что всё удалось.

Удаление водяного знака не решается настройкой параметров: в `biz_data` вообще нет поля watermark,
водяной знак вжигается в пиксели на цепочке рендеринга, возможна только постобработка с перерисовкой. Ключевые моменты реализации:

- **Нельзя использовать ffmpeg `delogo`**: он делает двунаправленную интерполяцию, горизонтальный размах 133 px затягивает блики на левой и правой границах
  целой полосой в середину кадра (по замерам на тёмном деревянном столе вытягивает заметную вертикальную светлую полосу). Для широких полосчатых областей интерполяцию нужно делать **с приоритетом по вертикали**.
- Полоса выборки смещена наружу на 2~3 px (строки вплотную к bbox ещё несут «послесвечение» сглаживания) + горизонтальный медианный фильтр (лечит «подсветку отдельного столбца»)
  + подбор шума (слишком чистая заполненная область, наоборот, бросается в глаза).
- Округление bbox до чётного должно идти **наружу**: `h -= h%2` превратит 41 в 40, нижняя граница водяного знака 697 дойдёт только до 696,
  остаётся белая точка в 1 px.

Конфигурация (**учётные данные — через переменные окружения, не записывайте их в репозиторий**):

```json
"storage": {
  "enabled": true,
  "endpoint": "https://oss.s3ai.cn",
  "bucket": "cdn",
  "public_base": "https://oss.s3ai.cn/cdn",
  "prefix": "qwen2api/videos",
  "strip_watermark": true,
  "quality": "near",
  "workers": 2
}
```

```bash
QWEN2API_STORAGE_ACCESS_KEY=... QWEN2API_STORAGE_SECRET_KEY=...
```

Замеры по ступеням качества (5,16 с / 720p / исходник 922 КБ): `near` 6,1 МБ / 1,7 с (по умолчанию, визуально без потерь);
`lossless` (qp=0) 21,7 МБ / 2,1 с — последняя ступень — единственная, при которой **пиксели вне области водяного знака остаются побитово неизменными**,
это проверено сравнением декодированных кадров, разница равна 0.

**Цепочка для изображений** (синхронная, без очереди) отличается от видео:

| | Видео | Изображение |
|---|---|---|
| Момент | Асинхронная очередь, внутреннее состояние `polishing` | Синхронная обработка до ответа |
| Алгоритм | Вертикально-приоритетная интерполяция YUV + горизонтальная медиана + подбор шума | **Зеркальное клонирование + растушёвка по четырём краям** (непрерывная текстура, лучше интерполяционных методов) |
| Сбой | После 3 повторов явно `failed` | **Это изображение не выдаётся**, без деградации |
| Цена | Перекодирование 1,7 с на ролик 5 с | Перекодирование PNG, 2,7 с на 2048² |

Общее для обоих: при сбое обработки **никогда** не откатываемся к прямой ссылке апстрима — это означало бы молча выдать артефакт с водяным знаком.

⚠️ Цена: образу нужен ffmpeg, размер вырастает с ~20 МБ до ~100 МБ.

## Суточная квота на генерацию изображений (локальное ограничение, по умолчанию 6 на аккаунт)

Бесплатные аккаунты апстрима по замерам дают около 9 изображений в сутки, но **при достижении жёсткого лимита апстрим не сообщает об ошибке** — лишь шлёт heartbeat и никогда не выдаёт результат,
о сбое узнаёшь только через 180 с. Поэтому шлюз сам ставит заслон заранее:

```json
"pool": { "max_image_per_day": 6 }
```

- Учитываются только **успешно сгенерированные изображения** (по замерам зависание не списывает квоту апстрима, засчитывать его значило бы впустую занимать место);
- **Сброс по календарным суткам** (у апстрима счёт «сегодня», а не скользящие 24 ч), при смене дня обнуляется автоматически;
- Квота **сохраняется между перезапусками** (записывается в `state_file`) — иначе перезапуск равен сбросу квоты, и апстрим будет пробит насквозь;
- После исчерпания сразу возвращается `429 insufficient_quota`, **к апстриму не обращаемся**, с пояснением, что это локальный лимит;
- Колонка «Сегодня изображений» в панели напрямую показывает `использовано/лимит`.

| Явление | Вывод |
|---|---|
| Набор заголовков неполный (особенно отсутствует `X-Accel-Buffering: no`) | Обязательно блокируется: `RGV587_ERROR::SM::哎哟喂,被挤爆啦` («ой-ой, перегружено!») + `punish?action=captcha` |
| В `chats/new` не хватает заголовков | **Не блокируется** (порог ниже) ⇒ «сессия создана успешно» не доказывает, что заголовки полны |
| Смена TLS-отпечатка на Chrome (curl_cffi) | При нехватке заголовков **всё равно блокируется** ⇒ проблема не только на уровне TLS |
| Ожидание 15 минут / смена аккаунта | **Бесполезно** ⇒ это не ограничение частоты и не блокировка аккаунта, а определение по признакам запроса |

**Вывод**: если дополнить 8 заголовков, которые страница явно выставляет на completions, + 2 заголовка bx, нативный TLS-стек Go
проходит стабильно (встроено в этот репозиторий, `internal/upstream/headers.go`). Если всё равно блокирует, сначала сверьтесь с
перечнем заголовков в `docs/UPSTREAM.md` §2.2, а не меняйте IP и не снижайте частоту.

## Честные границы

- **`mask` не пересылается**: у апстрима нет семантики inpaint. Если передан `mask` (вместе с `image`), по-прежнему вернётся 200, но локальная перерисовка **не** будет выполнена —
  так обстоит дело и в image-adapter; лучше пометить это в документации, чем подделывать возможность.
- **TTS / голос в реальном времени: явно не делаем** (есть доказательства, это не лень). `GET /api/v2/tts/config` возвращает только **каталог голосов +
  mp3 для прослушивания** (30 языков / 50+54 голоса), **эндпоинта синтеза нет**; после входа в «голосовой звонок» UI работает нормально, но
  три хука fetch / WebSocket / getUserMedia дали 0 попаданий, и среди 40 запросов CDP нет ни ws, ни audio —
  канал вне уровня HTTP (WebRTC). Чтобы это поддержать, нужно сначала реализовать клиент WebRTC + кодек Opus,
  а это уже не шлюз, а другой клиент. Подробности — `docs/UPSTREAM.md` §4.9.
- **Инструменты MCP (code interpreter / amap и т. п.)**: модель вызывает их по собственному решению, через кадры вызова инструментов.
  В этом репозитории уже умеют разбирать семейство `image_gen`; остальные phase **пишутся в журнал** (больше не отбрасываются молча), но в структурированные артефакты пока не переводятся.
- **Соответствие видеозадач сохраняется на диск**: `data/videos.json`, хранится 8 дней (ID задач апстрима живут 7 дней).
  Раньше хранилось только в памяти 2 ч, и при перезапуске терялись id в руках у клиентов — это нарушение контракта, исправлено.
- **Вызов инструментов эмулируется**: в веб-версии апстрима нет канала вызова функций. Шлюз рендерит `tools` в системный
  протокол («когда нужен инструмент, весь ответ — только один JSON»), затем разбирает вывод в `tool_calls`. Поэтому:
  ① это **адаптация протокола**, а не нативный function calling — модель теоретически может не соблюдать его;
  ② если разбор не проходит (выдуманное имя инструмента, битый JSON, пустой массив) — всегда **откат к обычному тексту**, вызов никогда не подделывается;
  ③ потоковый путь требует, чтобы модель начинала ответ с `{` или блока кода, иначе тот же вывод распознаётся только в непотоковом режиме
  (протокол прямо этого требует, по замерам соблюдается 5/5);
  ④ при наличии `tools` **принудительно отправляется полный prompt** (блок протокола должен быть виден на каждом раунде, инкремент привёл бы к потере протокола на втором раунде),
  а модель agent деградирует к базовой обычной модели (по замерам она обходит клиентские инструменты собственным веб-поиском);
  ⑤ на каждом раунде выдаётся `X-Qwen2API-Warnings: 工具调用由网关模拟…` («вызов инструментов эмулируется шлюзом…»);
  ⑥ размер набора инструментов — **нормальная особенность клиента** (чем больше MCP, тем он больше). Бюджет по умолчанию 32 КБ/256 штук, при превышении
  только пропускается эмуляция, запрос не отклоняется — урок 20.11.2026: в первой версии жёстко зашили 64 КБ, WorkBuddy в режиме
  «полный доступ» принёс 89 154 байта и сразу превратил `qwen4-max-agent` в недоступную с ошибкой 400.
  Порог 32 КБ выбран потому, что **больше невыгодно**: по замерам 94 КБ / 28 инструментов (по 40 параметров у каждого): первый байт
  7,3 с, общее время 45,8 с, а кадров `tool_calls` — **0** — каталог слишком велик, модель вообще не вызывает инструменты, остаётся лишь задержка.
- **Без очереди**: при нехватке ёмкости сразу 429 (это синхронная цепочка, очередь лишь заставит клиента думать, что всё зависло).
- **Многораундовость через сплющивание**: шлюз без состояния, на каждый запрос создаётся новая сессия, история склеивается в единый prompt. Оптимизация, экономящая токены, —
  «переиспользование chat_id + цепочка parent» — относится к последующим доработкам, сейчас не делается (риск смешения контекстов > один вызов апстрима).
- **Срок жизни токена неизвестен**: полагаемся на пассивное истечение по 401 + охлаждение, длительность не угадываем.
- **`/v1/messages/count_tokens` — оценка** (CJK 1:1, ASCII 4:1), точность не изображаем.

## Выпуск версий

push в `main` → тесты → автоинкремент patch (`v0.0.x`) → сборка мультиархитектурного образа (amd64 + arm64) →
отправка в GHCR (три тега: версия / `sha-` / `latest`) → аннотированный tag → создание Release.
Аварийный выход: commit message содержит `[skip release]`; ручной номер версии — через `workflow_dispatch`.

```bash
docker pull ghcr.io/yuanjie-ai/qwen2api:latest
```
